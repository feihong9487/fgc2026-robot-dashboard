FGC 2026 儀表板方案

2026-09-06距比賽（10/6–10/10 仁川）4 週依 Game Manual 6/24 版、TRG 6/29 版、SDK 11.1.0 位元碼查證，經三輪獨立反駁修正

要不要改用 Android Studio？

不用。你要的兩件事（儀表板看即時狀態、C270 做 AprilTag）在 OnBot Java 裡就做得到：SDK 11.1.0 給 OnBot Java 的編譯環境已內含 NanoHTTPD、Java-WebSocket、gson、VisionPortal、AprilTagProcessor 與 @WebHandlerRegistrar 等 hook。反駁者已用這套 classpath 離線編過整份 teamcode 與一支探針檔。Android Studio 可以留著當編輯器，但不要用自建 APK 取代 Control Hub 上的官方 RC app。

VMX 儀表板要改多少？

協定層不換，加一個 FGC profile。Chart、全部訊號、控件庫共 745 行零改動；RobotClient 與 store 共 401 行小幅修改（約 70 行）；新增 4 個 FGC 分頁。「全部訊號」分頁對任何 /FGC/… key 零改動就能顯示、釘選波形。

AprilTag 怎麼做？

C270 鎖 640×480、用官方標籤庫、相機裝在 450 mm 以下、主線只做「距離→射速提示」。官方 jar 沒有座標，我已從官方 STEP 檔解出 5 個標籤的場地位姿（下表）。但 AprilTag 在正賽的邊際價值有限，Skills Challenge 的計分算術對射球不利，所以它是第 3 週的加分項，而且 9/13 前沒有標定牆就整組砍掉。

一、為什麼不走 Android Studio

規則上它不是禁止：R17 的本文只要求 Control Hub OS 1.1.6、RC／DS app 11.0 以上；「should program using Blocks or OnBot Java… support will not be available」是規則後的註解方塊。真正的問題有三個。

檢錄檢錄清單尚未公布（TRG Appendix E 全是 Details to be provided）。這是唯一在檢錄台上「看得見」的差異。逐字滿足 R17 註解；被問時可打開 OnBotJava 頁面給裁判看原始碼。

二、建議架構：只用 Control Hub 既有的 8080 與 8081

三位評審一致選這條路，關鍵理由是「不自己開任何 socket」。自開 port 在 OnBot Java 環境有一個我從位元碼證實的陷阱：每次 Build Everything 會換新的 ClassLoader，SDK 會把舊類別的 hook 從清單移除（AnnotatedHooksClassFilter.filterOnBotJavaClassesStart → removeOldMethods），舊類別開的 ServerSocket 卻還活著佔著埠，新類別看不到它、關不掉它，結果就是 Address already in use。用 SDK 自己管理的 8080／8081 完全避開這一類故障。

資料流

  • 上行遙測：OpMode 每圈呼叫 DashHub.put("/FGC/Shooter/SL", v)（只寫 map）。DashPublisher 每 50 ms 把有變化的 key 用 gson 組成 JSON，對自己維護的 socket 集合逐一 send；每 2 秒送一次全量 hello 當 keepalive 兼補值；沒有人訂閱就整輪跳過。
  • 下行寫回：前端送 {"namespace":"dash","type":"set","payload":"{k,v}"}。handler 只把字串丟進 inbox，OpMode 執行緒 drain 後由 DashParams 做白名單、範圍夾限、MATCH 拒絕，再寫進 Constants 的 volatile 欄位，並回推 /FGC/Param/… 讓 UI 顯示機器人實際採用的值。
  • 影像：/dash/stream.mjpg 用 NanoHTTPD.newChunkedResponse 送 multipart/x-mixed-replace，每格用 VisionPortal.getFrameBitmap 取圖，JPEG 壓縮在 pump 執行緒做（放在 Continuation 的 consumer 裡會卡住視覺管線）。機器人端發布 /CameraPublisher/C270/streams = ["mjpg:http://192.168.43.1:8080/dash/stream.mjpg"]，前端現成的 resolveStreamUrl 零改動就能找到它。瀏覽器對 chunked multipart 的行為尚未實測，所以保留 /dash/snapshot.jpg 單張輪詢當退路。
  • 前端：RobotClient 連 ws://192.168.43.1:8081，開啟後先送 {"namespace":"system","type":"subscribeToNamespace","payload":"dash"}，把收到的 hello/nt 的 payload 解成 JSON 後餵 store.applyBatch。訂閱失敗 SDK 只在機器人端 log、不回錯，所以 2 秒沒收到 hello 就重送；3 次失敗自動切成輪詢 /dash/state.json。所有 /dash/* 一律是無自訂標頭的簡單 GET，因為 RC 的 web server 不處理 OPTIONS preflight。

五條必須照做的工程規則

這五條全部來自位元碼查證與反駁階段，每一條漏掉都會產生「看起來像網路壞了」的難查症狀。

  1. 狀態放 System.getProperties()。OnBotJava 每次 Build 換新 ClassLoader，但已註冊在 WebHandlerManager／WebSocketManager 的 handler 是舊實例。latest／inbox／錄影緩衝放自己的 static 欄位會在 Build 後凍結。放進 Properties（boot ClassLoader）就跨得過去，值只用 JDK 型別、SDK 型別與字串。
  2. 註冊的 handler 只是薄殼，邏輯放在可替換的委派物件上。狀態共享只救了資料，救不了程式碼：舊 handler 呼叫的 DashParams、DashMjpeg 仍是舊 ClassLoader 的類別。所以 @WebHandlerRegistrar 註冊的六條路徑與 namespace handler 一律只做一件事：從 Properties 取出一個實作 SDK 介面（WebHandler、WebSocketNamespaceHandler，都是 app ClassLoader 的型別，可跨 ClassLoader 轉型）的委派物件並呼叫它。每支 OpMode 的 init 都重新放入最新的委派物件，因為 OpMode 永遠是最新編譯結果。這樣改 DashParams／DashMjpeg 只要 Build + 重跑 OpMode，只有薄殼本身（寫一次不再動）要重開電源。
  3. 執行緒要有世代號。@OnCreateEventLoop 每次 Restart Robot 都跑，Build 後舊 ClassLoader 的推播執行緒還活著、還在 drain 同一個 inbox，而你拿不到它的參考。Properties 裡放一個 AtomicLong gen，每次啟動先 incrementAndGet，推播／pump／錄影 flush 迴圈每圈比對世代不符就自行結束；ExecutorService 也放進 Properties，新世代先 shutdownNow 舊的。把活著的執行緒數發布成 /FGC/Bridge/Threads，不是 1 就是出事了。
  4. 自己維護 socket 集合，不依賴 broadcastToNamespace。在 namespace handler 的 onSubscribe／onUnsubscribe 維護一個 CopyOnWriteArraySet<FtcWebSocket>（放 Properties），推播時逐一 isOpen() 後 send，每圈包 try/catch(Throwable)。這同時消掉 namespace 未註冊時的 IllegalStateException、讓退路 B（8080 掛不上時）真的能推資料，也不再需要 WebSocketManager。namespace 用 WebSocketNamespaceHandlerRegistry.registerNamespaceHandler（public static，OnBotJava classpath 已有）註冊，包 try/catch(IllegalArgumentException) 防重複。
  5. 總開關是執行期旗標，不是編譯期常數。public static final boolean ENABLED 會被 javac 常數摺疊，而且 Build 不會重跑 @WebHandlerRegistrar、WebHandlerManager 也沒有 unregister，所以「改常數 + Build」關不掉任何東西。改成每個 handler 進來先讀 System.getProperty("fgc.dash.enabled")，不是 "1" 就回 404、不推播；再寫一支 5 行的 OpMode「Z-DASH-OFF」把它設成 "0"。關閉 = Driver Hub 選一個 OpMode，5 秒，可當場示範。

另外四條硬體與 I/O 規則

  • Bulk read 開 MANUAL 模式。DcMotorEx.getCurrent 與 voltageSensor.getVoltage 都不在 bulk read 內，每次都是一趟阻塞的 Lynx ADC 指令。現有程式每圈已有 6 次 getVelocity／getPosition，再加電流電壓會撞上 loop ms 25 ms 的驗收線。第 1 週埋點時就對所有 LynxModule 設 BulkCachingMode.MANUAL、每圈開頭 clearBulkCache()；電流電壓改 2–5 Hz 輪流取樣；卡球偵測用 bulk read 內免費的 isMotorOverCurrent。
  • OpMode 監聽要持強參考。OpModeManagerImpl.listeners 是 WeakReferenceSet，只 register 不持有會在 GC 後靜默消失。監聽物件放 Properties。錄影不靠 PostStop 收尾：每 10 秒 append 到帶時間戳的檔案，PostStop 只做最後 flush；比賽中拔電池最多掉 10 秒。
  • MATCH 模式什麼都不推。筆電留在 pit 時，pit 裡的人若還看得到即時數據再對場邊比手勢，就是 M11。MATCH 模式下 WebSocket 不推、/dash/state.json 回 503、MJPEG 回 503、CameraStreamServer.setSource(null)（Driver Hub 的預覽走 robocol，比 MJPEG 更會排擠控制訊號），只寫錄影。
  • OpMode 名稱與 telemetry 全用 ASCII。OnBotJava 的 javac 編碼與 Driver Hub 對 CJK／符號的渲染都沒驗證過，現場排錯時一串看不懂的字只會拖慢志工。用 A1-MATCH／B1-PIT／Z-DASH-OFF／Z-FALLBACK-v2，telemetry 用 READY／SPINUP。中文只留在儀表板前端。

Day 1（Control Hub 上線後 30 分鐘）

整個方案只有一個尚未在實機證實的假設：OnBotJava 編譯出來的類別，其 @WebHandlerRegistrar 真的會被呼叫。SDK 位元碼顯示會，但要把它變成已知。

  1. OnBotJava 新增 DashPing.java：@WebHandlerRegistrar 註冊 /dash/ping 回 {"pong":時間,"tag":"v1"} 並加 Access-Control-Allow-Origin: *；用 WebSocketNamespaceHandlerRegistry.registerNamespaceHandler 註冊 "dash"（onSubscribe 回 hello），起一條執行緒每秒對集合裡的 socket send 一個計數。
  2. Build Everything → 重開 Control Hub 電源一次（Restart Robot 不會重跑 8080 的註冊）。
  3. 檢查 A：瀏覽器開 http://192.168.43.1:8080/dash/ping。
  4. 檢查 B：F12 console 貼 
    const w = new WebSocket("ws://192.168.43.1:8081");
w.onopen = () => w.send(JSON.stringify({namespace:"system", type:"subscribeToNamespace", payload:"dash"}));
w.onmessage = e => console.log(e.data);
    要先印一則 hello，之後每秒一則 nt。
  5. 檢查 C（委派替換）：把 tag 改成 v2，Build，跑一次任何 OpMode（init 會刷新委派），不重開機，/dash/ping 應顯示 v2。顯示 v1 代表薄殼沒有正確取委派。
  6. 檢查 D：按 Restart Robot 兩次，兩次都不通才算失敗（OnBotJava 重掃在背景執行緒，第一次可能跑到舊 hook）。
  7. 檢查 E：Build 後不重開機直接打舊的 /dash/state.json，看 logcat 有沒有 NoClassDefFoundError（判定舊 dex 是否被刪）。

判讀：A、B、C 全過 → 剩下的都只是填內容。B 不過 → 只用 8080 輪詢（前端 40 行），功能不減、延遲 100 ms。A 不過（且確實重開過電源）→ 8081 仍能推播與收 set，錄影改從 OnBotJava 檔案樹下載，只損失 MJPEG。三種結果都不需要 Android Studio。

Day 2（15 分鐘）

寫一個假影像 handler（每 100 ms 產一張純色 JPEG），Chrome 直開 /dash/stream.mjpg 看到連續變色才算 MJPEG 這條路通；不通就直接走 snapshot 輪詢。三份設計都把這件事當已知，其實從沒驗證過。

六、AprilTag 計畫

硬體與規則

  • C270 在 BOM（REV-39-1598）內，合法，但最終機器人上只能 1 台（R10 數量限制），備品可買不可同時裝。
  • 不能加 USB 延長線或 hub 的依據是 R10／R11（只能用套件內元件，BOM 沒有任何 USB 線）；R13 管的是不剪線、不拆接頭、不改電子件。1.5 m 原線直插 Control Hub USB-A，餘線用套件束帶固定。
  • R19 要求依 REV Wiring Diagram 佈線，該圖不在三份 PDF 內，是否畫了相機接法要另外確認（見去函問題）。
  • 相機光心離地毯 ≤450 mm。R04 要求開賽時整台機器人在 50×50×50 cm 內，S01 讓它同樣適用 Skills。標籤中心在 791 mm，Δz 約 340 mm，2 m 處仰角 9.7°、3 m 6.5°、4 m 4.9°，對姿態解算影響很小；量到的實際高度記成 CAM_Z_MM。

你的機構：前射後吸，相機正置在 shooter 前方正中間

  • 相機軸線就是射擊軸線：ftcPose.bearing 直接等於瞄準誤差，setCameraPose 不需要 yaw 偏移，只要量相機光心相對機器人中心的 x／y／z（mm）。AimAssist 與射距提示都少一層換算。
  • 車頭方向：現有 TeleOp 開局預設「吸取端為前」，射擊時掉頭面向 SU，相機這時正對標籤，與設計吻合；儀表板的 /FGC/Drive/Reversed 要一起顯示，回放時才分得出「當時相機朝哪」。
  • 鏡頭在射線正下方：每顆球出膛都會掃過畫面上緣，偵測會短暫中斷，靠「連續 3 幀」與 Age 累加吸收，不要把單幀消失當成沒看到標籤。鏡頭要低於球道且加防護，避免回彈球直接打到 C270（它不能換、不能修，R13）。
  • R04 現在就量：機構已裝完，今天用捲尺量相機光心離地高度與 50 cm 立方體是否包得住，結果寫進 CAM_Z_MM；不合格改的是支架不是程式。
  • 排程受益：機構完成代表第 1 週的實機驗證（推搖桿、扣 R2 看轉速）不再被組裝卡住，第 3 週原本留給機構延誤的緩衝可以還給 AprilTag 標定。

軟體設定

  • 解析度鎖 640×480：SDK 內建校正只有這組（fx=fy=822.317，cx=319.495，cy=242.502）。不要呼叫 setLensIntrinsics，啟動後 logcat 不能出現 "User did not provide a camera calibration"。代價要說清楚：160 mm 標籤在 d 公尺處畫面寬約 822×0.16/d 像素，2 m≈66 px、4 m≈33 px、6.3 m（對面出發點到標籤）≈21 px 已在偵測門檻。640×480 的實際可信距離大約 4.5–5 m，第 3 週要實測寫下來；若不夠，用棋盤格手動校正 1280×720 再 setLensIntrinsics（半天），640×480 當回退。
  • 官方標籤庫：IgnitingInnovationAprilTagLibrary-1.0.jar（單一類別、不與 RC app 重名）用 OnBotJava 的 Upload Files 上傳，global.first.IgnitingInnovationGameDatabase.getIgnitingInnovationTagLibrary()。它只有 ID／名稱／160 mm，沒有座標，robotPose 會是 null。要場地座標時用六參數 addTag(id, name, 0.160, VectorF, METER, Quaternion) 把下表餵進去再 setCameraPose。
  • decimation 做成 /FGC/Tune/TAG_DECIMATION 即時可調，在 pit 掃 1／2／3，取「偵測率 >90% 且 fps >15」的最大值。預設 3 會把 4 m 砍到約 11 px 抓不到。
  • 過濾：decisionMargin <30 丟棄、同一 id 連續 3 幀才採信、每個 id 發布 Age 秒（沒看到讓 Age 累加，不要讓數值消失被誤讀成距離 0）。

用途，誠實排序

  1. 遙控時的射距提示：range → 建議射速插值表，送到 Driver Hub telemetry（DS 是唯一合法的場上顯示裝置），要不要採用由駕駛決定。這是 AprilTag 在正賽唯一乾淨的用法。
  2. AimAssist（可選）：按住 L1 才把 bearing 以 P 疊加到 turn，放開完全回手動。永遠不代按扳機。G13：故意把球射向機器人、人或場外是 RED CARD；同聯盟三台機器人共用一個 SU，隊友常在射線上。VEL_SL／VEL_SR 的 clamp 上限要用幾何（SU 頂 2009 mm、頂棚外伸 400 mm）算出不越頂的物理上限，並訓練「隊友在射線上就不射」。
  3. Skills Challenge 不用 AprilTag。計分 = 分數 ÷ 秒；CLIMB 四檔 50／110／130／150 分，球只有 1／5／2 分，場上只 staged 六顆球（S07，最多 36 分），G06 不能預裝。純爬到 ZONE 3 若 15 秒是每秒 10 分，加射六球多花 60 秒反而掉到每秒 2.5 分。Skills 的最佳解是直衝 BRACE 爬升，S05 允許遙控，練過的駕駛比自動更快更穩。原本規劃的 SkillsAuto 刪除，時間改投爬升機構可靠度。
  4. 不做：MATCH 中的全自動瞄準。正賽是 500 顆球、每顆 1 分、CLIMB 是乘數的吞吐量遊戲，決定分數的是裝填與投放速度。

標定驗收

2.0 m 處 range 誤差 <10 cm、標準差 <3 cm；正對時 |bearing| <3°；fps ≥10。誤差隨距離線性放大 = 標籤印錯尺寸；固定偏移 = 相機安裝面到光心的距離沒扣。bearing 先確認符號再調任何 P 增益。開串流前後看 VisionPortal.getFps()，掉超過 20% 就降規格（loop ms 抓不到視覺執行緒的退化）。

七、比賽日模式

核心設計：比賽日的儀表板是「錄影機 + 賽後回放器」。MATCH 期間機器人不推播、不開相機、拒絕所有寫回，只在自己身上錄影；筆電留在 pit，賽後回 pit 下載回放。

規則風險對策
M06 場邊不得複雜設定
WHITE CARD		到場邊才開機、連 Wi-Fi、等串流。橋接器隨 RC app 常駐，場邊唯一動作是 Driver Hub 選 A1-MATCH。筆電不進場邊。Control Hub 改名後在 pit 重存 Wi-Fi profile。

YELLOW CARD		pit 裡的人看即時數據再對場邊比手勢。MATCH 模式根本不推播，pit 裡看不到即時數據；比賽中真正需要的判斷（READY、距離、建議射速）放在 Driver Hub telemetry。

八、風險表

風險可能性對策
訂閱時 namespace 還沒註冊，SDK 不回錯，前端看起來連上卻沒資料。高onSubscribe 立刻回 hello；前端 2 秒沒收到就重送；頂欄顯示「等待 dash namespace」而不是綠燈。
Build 後 handler 邏輯凍結在舊 ClassLoader（症狀像「改了 clamp 沒生效」）。高（不做委派必然發生）薄殼 + 委派物件放 Properties，OpMode init 刷新；Day 1 檢查 C 專門驗這件事。
Build 後舊推播執行緒還活著，值亂跳、set 時靈時不靈。高（不做世代守衛必然發生）世代號 + shutdownNow 舊 executor；HealthPanel 顯示 Threads，不是 1 就出事。
改 DashBridge 忘了重開機，誤判成「這條路不通」。中DashBridge 寫一次不再動；文件寫死「改 DashBridge → 重開 Control Hub」；Restart Robot 一律按兩次。
電流電壓每圈讀取撞上 loop ms 25 ms 驗收線，第 4 週才發現。高Bulk cache MANUAL；電流電壓 2–5 Hz；isMotorOverCurrent 做卡球；第 1 週就量對照。
OpMode 監聽被 GC 回收，比賽日錄影不產生。中監聽物件持強參考；錄影每 10 秒 flush，不靠 PostStop；HealthPanel 顯示錄影行數在動。
MJPEG 吃 CPU 或頻寬，手感變鈍或視覺 fps 掉一半。高（若不設限）10 fps／q40／1 條；壓縮在 pump 執行緒；MATCH 回 503；同時看 loop ms 與 VisionPortal.getFps()。
瀏覽器對 chunked multipart 顯示不穩。未實測Day 2 驗；snapshot.jpg 輪詢退路。
